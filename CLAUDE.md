# Client Portal

Monorepo with two applications:

- `backend/` — .NET 10 API (Clean Architecture), PostgreSQL
- `frontend/` — Next.js 16 (React 19, Tailwind 4, TypeScript)

Code, identifiers, code comments and commit messages are in English. Reply to the user in the language they write in.

## Product plan

The product vision, feature list and MVP scope are in [.claude/docs/product-plan.md](.claude/docs/product-plan.md) (written in Romanian). Read it at the start of a new feature or when unsure about scope. The decisions already taken (with their reasons) are in [.claude/docs/decisions.md](.claude/docs/decisions.md), one section per area: read only the section relevant to the current step.

- The user builds this **step by step, to understand it and catch problems along the way**. Work in small steps, explain the why briefly, and do not jump ahead to features outside the current step or build the whole MVP at once.
- After finishing a step, tick it in the `Progres` section of the plan; record architecture / data-model decisions in the matching section of `decisions.md`.
- Stick to the MVP list; proposals, payments, advanced automations, CRM, AI, white-label and extra integrations come later.

## Working rules

- **After every change, suggest a short commit message** in case the user wants to commit right then. Format: `type: summary` (e.g. `feat: add client registration endpoint`), single line, imperative mood. Types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`.
- **Never run `git commit` / `git push` on your own.** Only on explicit request; just propose the message.
- **Comments are sparse and short.** Write one only for a non-obvious *why* (a security reason, a workaround, an invariant the types cannot show), one line when possible. No comment that restates the code or a name, no `<exception>` / `<param>` boilerplate on interfaces, no narration of steps. A better name beats a comment.
- Do not run destructive commands (reset --hard, deleting folders, `docker compose down -v`) without confirmation.
- Verify before saying it's done: `dotnet build` with zero warnings and a green `dotnet test` for the backend; `pnpm lint` for the frontend.
- If something could not be tested (e.g. Docker/DB unavailable), say so explicitly.
- Personal preferences that should not apply to everyone belong in `CLAUDE.local.md` (git-ignored), not here.

## Frontend (`frontend/`)

- Next.js 16 has **breaking changes** compared to what you know. Before writing code, read the relevant guide in `frontend/node_modules/next/dist/docs/` (see `frontend/AGENTS.md`).
- Commands (from `frontend/`): `pnpm dev` (localhost:3000), `pnpm build`, `pnpm lint`.
- Calls the backend API at `http://localhost:5051` (override with the `BACKEND_URL` env var). The browser never calls it directly: `next.config.ts` rewrites `/api/*` to the backend, so the session cookie belongs to the frontend's own origin and no CORS is involved. Server Components call the backend directly with the session cookie forwarded.
- **Auth**: pages and forms are in `src/app/(auth)/` and `src/components/auth/`; the session logic is in `src/lib/auth/`. `src/proxy.ts` (Next 16's name for middleware) only does a quick redirect when the session cookie is missing. The real check is `requireUser()` (calls `GET /api/auth/me`), which every protected page must call itself: layouts are not a safe place for it, see the Next.js authentication guide.
- **Workspaces**: `/` only redirects (no workspace → `/workspaces/new`, one → `/w/{id}`, several → `/workspaces`). Workspace pages live under `src/app/w/[workspaceId]/` and call `getWorkspace()` (`src/lib/workspaces/server.ts`), showing `notFound()` when it returns null. Server-side API calls go through `serverFetch` (`src/lib/api/server.ts`), browser-side ones through `sendJson` (`src/lib/api/client.ts`).
- **App shell** (`src/components/shell/`, plan in [.claude/docs/ui-redesign.md](.claude/docs/ui-redesign.md)): every signed-in page sits in a sidebar. `AppShell` (server) loads the user, the workspaces they work in and the ones they are a client of, and renders `AppSidebar` (client: it needs `usePathname`, so it only receives serializable data, `ShellContext` in `types.ts`). Three layouts feed it: `app/w/[workspaceId]/layout.tsx` (`kind: "workspace"`, with up to 5 Active projects), `app/portal/layout.tsx` (`kind: "portal"`) and `app/(shell)/layout.tsx` (`kind: "none"`: `/account`, `/workspaces`, `/workspaces/new`). The menus are in `nav.ts`: an item without `href` is a future feature and shows disabled with a "Soon" badge, so turning one on means giving it an `href`. `ContextSwitcher` (workspaces / "Client of") is the sidebar header, `NavUser` (Account, Theme, Sign out) the footer. A page starts with `<Page crumbs={[...]}>` (`Page.tsx`: top bar with the sidebar toggle and breadcrumb, then the content column; `narrow` for forms) and must not render its own `<main>` (the shell's `SidebarInset` is it). Layouts do not re-render on navigation, so a mutation that changes what the sidebar shows (a new project) calls `router.refresh()`. Dark is the default theme (`theme-provider.tsx`). In e2e tests the sidebar's links are under `mainNav(page)` and the breadcrumb under `breadcrumb(page)` (`e2e/helpers.ts`); project names also appear in the sidebar, so look for links inside `getByRole("main")`.
- **Dashboard** (`app/w/[workspaceId]/page.tsx`, blocks in `src/components/dashboard/`, rules in `src/lib/dashboard/deadlines.ts`): "Needs your attention" (projects with `approvals` to act on or wait for, changes requested first), "Coming up" (deadlines of projects and unfinished stages within 14 days, plus late ones), "Active projects", "Waiting on clients" (invitation sent or expired); a workspace with no projects sees `GettingStarted` instead. Built from `getProjects` and `getClients`, no endpoint of its own.
- **Projects**: `src/app/w/[workspaceId]/projects/` (list, `[projectId]`; a new project is made in a dialog, `NewProjectDialog`, with the client preselected when opened from a client's page), components in `src/components/projects/`, data in `src/lib/projects/`. A client's page lists that client's projects with the same `ProjectsTable`.
- **Project page** (`app/w/[workspaceId]/projects/[projectId]/page.tsx`): a header row with the name, the status and an "Edit project" button on the right, the client, then `ProjectTimeline` (below) and `ProjectTabs` (`src/components/projects/`, client) with two tabs: Overview (`UpdateList`, and beside it `ProjectApprovalsCard`) and "Deliverables & Files" (`DeliverableList` and `FileList` side by side on wide screens), each tab's content rendered on the server and handed in as `panels`. Editing the project (`ProjectForm`) and archiving it are in a `Sheet` (a panel over the page) that wraps the whole page, so any `SheetTrigger` inside opens it: the header button and the deadline card's "Set dates". The panel is modal: in e2e tests `openEditor(page)` (`e2e/helpers.ts`) opens it and Escape closes it before anything behind it is used. Only the open tab is mounted, so a half-filled form does not survive a tab switch. The open tab is in the address (`?tab=deliverables`, none for Overview): it is read with `useSearchParams` and changed with `window.history.replaceState`, which Next syncs with the router without asking the server. `GoToTab` is a button inside any panel that opens another tab. The page is keyed by project id, so moving to another project starts on Overview. **`ProjectTimeline`** sits above the tabs, so both show it: one bar for the whole project with each stage a segment laid out by its dates (`buildTimeline` in `src/lib/projects/timeline.ts`, pure and tested without a browser in `e2e/timeline.spec.ts`: widths follow the dates only when the project has a start and an end, otherwise the stages share the bar evenly; a minimum width keeps a short stage clickable), a "Today" marker, "N of M done" and the days left or overdue. **The stages are edited on the bar itself** (there is no stage list on the page, and no way to reorder: the bar draws the stages **by due date**, `orderByDate` in `src/lib/projects/timeline.ts`, a stage without a date keeping its place in the list; the portal's stage list and `summarize` use the same order), only for the freelancer on a project that is not archived (`editable`): a segment is a button (`StagePopover`, client) that opens a menu centred under it where **everything is edited in place and saved as it is left**: the name (an input styled as a title; emptying it is refused with a message), the status (a three-button control, saved at once), the due date (picked on a calendar, saved at once), the description (saved on blur) and Delete (confirmed inside the menu); every save sends the whole draft so fields never overwrite each other, and closing the menu flushes what is pending; the + at the end of the bar (or "Add the first stage" on an empty one) opens `AddStageDialog`; **a stage's date has to be inside the project's** (`limits` from `lib/projects/limits.ts`) and is **picked on a calendar, never typed**: `DatePicker` / `DateField` (`src/components/forms/`, a popover with shadcn's `Calendar`, i.e. `react-day-picker`) greys out and refuses the days outside the limits and stops paging at the project's first and last month, and the API refuses a date outside it too; the menu's date saves as soon as a day is picked (in e2e tests `pickDate` / `calendarDay` in `e2e/helpers.ts` find a day by `data-day`, which is the en-US date); and in "time" mode the edge between two stages has a `StageDateHandle` (appears on hover, always on touch) that is dragged or moved with the arrow keys (Shift: a week) to change that stage's due date, never past its neighbours' dates, saved on release (keys: 700 ms after the last press); while dragging, the part the stage gains or loses is shown hatched. Every change is one request through `useStageRequest` (the API answers with the whole project) and then `router.refresh()`. "Set dates" is a `SheetTrigger` passed in as `datesAction`. The same component, read-only, sits above the tabs of the client's project page. `ProjectProgress` (the small "N of M done" under one segment per stage) is what the lists use. In e2e tests click the tab first (`openTab(page, "Deliverables")`).
- **Adding to the project page's sections** (Updates, Deliverables, Files, and the stages on the bar) is asked for, never left on the page: a button in the section header (and "Add the first …" in the empty message; Files has a permanent drop area instead) opens a dialog with the form; in e2e tests look for the fields in `page.getByRole("dialog", { name: "Add an update" })` (or "Add a deliverable", "Upload a file", "Add a stage").
- **Deliverables**: the "Deliverables" section on the project page (`src/components/deliverables/`, data in `src/lib/deliverables/`). `getDeliverables()` loads archived ones too; the owner restores them from the same list. Each row also shows where its approval stands (`ApprovalSummary`: the status badge, the client's message, and every round in a `<details>`) and the "Request approval" (`ApprovalRequestForm`, optional note) / "Withdraw request" buttons; while a request is open Edit is replaced by Withdraw, and a deliverable with approvals has no Delete.
- **Clients**: `src/app/w/[workspaceId]/clients/` and `src/components/clients/`. The list is `ClientsTable` (client: search and the Active / Archived tabs filter what the page already loaded, the scope is in `?archived=1`; each row has an avatar, the open projects count computed in the page from `getProjects`, and the portal status). A client's page has a profile header (`ClientAvatar`, status, mailto / tel links), the client's projects, and in the right column `ClientPortalCard` (one short status line and the invitation buttons; the long explanation is an `InfoTip`, and "when this client was added" is another one next to the status badge) and `ClientNotesCard`; editing and archiving are in the "Edit client" `Sheet`.
- **Updates** (the timeline's written notes): the "Updates" section on the project page, under Deliverables (`src/components/updates/`, data in `src/lib/updates/`). Same shape as deliverables: `getProjectUpdates()` loads archived ones too, the owner restores them from the same list.
- **Files**: the "Files" section on the project page, under Updates (`src/components/files/FileList.tsx`, data in `src/lib/files/`): upload (a drop area is always at the top of the section, the one exception to "adding is asked for": click to browse or drop a file on it, or anywhere on the section, and a dialog opens with that file chosen, where it is named and given a note, 25 MB; the dialog's own `FileDropzone` swaps the file; the area is hidden on an archived project), download, Share / Unshare, Edit (name and description, the file itself is never replaced), Archive / Restore (owner) and Delete (a draft only). They are not deliverables and have no approvals. `getProjectFiles()` loads archived ones too. Uploads go through `sendForm` (`src/lib/api/client.ts`); `next.config.ts` raises `proxyClientMaxBodySize` because Next cuts a proxied body at 10 MB. Downloads are plain `<a download>` links to the API (it answers with an attachment).
- **Clients' side**: `/invite/[token]` (in `src/app/(auth)/`, public, listed in the `proxy.ts` matcher exclusions) opens an invitation and a client's portal is per firm: `/portal` only redirects (to the first firm they are a client of, or explains there is none yet), `/portal/[workspaceId]` is that firm's home (a welcome line, "Waiting for you" with a link per deliverable to the project's Deliverables tab, "Active projects" with `summarize`'s Right now / Up next, and "Latest updates" across the firm's projects; it loads each project with `getPortalProject`, in parallel) and `/portal/[workspaceId]/projects` its projects (`PortalProjectList`; `getPortalWorkspace()`, `getPortalProjects()` in `src/lib/portal/server.ts`; the layout `app/portal/[workspaceId]/layout.tsx` answers 404 for a firm the person is not a client of), and `/portal/[workspaceId]/projects/[projectId]` is one project (404 under any firm but its own), on `ProjectTabs` (shared with the freelancer's page; it takes the list of tabs): Overview (description, progress, the three latest updates, stages), Deliverables (hidden while none is shared; its tab badge counts the ones waiting for the client), Updates (the five latest open, the rest in a `<details>`) and Files (hidden while none is shared; `PortalFileList`, download links to `/api/portal/projects/{id}/files/{fileId}/download`). A project that waits for the client's answer shows a "Waiting for you" banner on Overview (`awaitingApproval`, its button opens Deliverables), and the `/portal` list a "N waiting for you" badge. In e2e tests click the tab first (`openTab(page, "Updates")`). Each deliverable carries `PortalApprovalPanel` (`src/components/portal/`): the freelancer's note, "Approve" (behind a confirmation, the answer is final) and "Request changes" (a message is required), and the earlier answers in a `<details>` (`getPortalProject()`, wording in `src/lib/portal/summary.ts`). `/` sends someone with no workspace of their own but a client link to `/portal`.
- **E2E tests** (Playwright, in `frontend/e2e/`): `pnpm test:e2e` from `frontend/`. One-time setup: `pnpm exec playwright install chromium`. Nothing needs to be started by hand, but Postgres, Mailpit and the file storage (RustFS) must be running (`docker compose up -d` in `backend/`; the run stops with a clear message if Mailpit or the storage is missing, because invitations send real SMTP and the tests read the emails back from it, and the file tests upload to the bucket `client-portal-e2e`, created on first use), with the dev credentials (user secrets or `appsettings.Development.json`) and `dotnet-ef` installed. A run compiles the API into `frontend/e2e/.artifacts`, **recreates the separate database `client_portal_e2e`** (never the dev one: `e2e/start-api.mjs` refuses any database name that does not end in `_e2e`), starts the API on port 5151 and a production build of the frontend on 3100, so it can run while the dev servers are up. Override the database with `E2E_POSTGRES_CONNECTION`. Add a test when a new user-facing flow lands.
- **UI is built with [shadcn/ui](https://ui.shadcn.com)** on Base UI primitives, style `base-nova` (see `components.json`). Add components with `pnpm dlx shadcn@latest add <name>` (from `frontend/`); they land in `src/components/ui/` and are only edited on purpose. Use them before writing custom UI.
  - Base UI, not Radix: composition uses the `render` prop, not `asChild`. A link that looks like a button is `<Link className={buttonVariants()}>`, not `<Button render={<Link />}>` (Base UI's Button would replace the link role).
  - Theme tokens live in `src/app/globals.css` (switch preset with `pnpm dlx shadcn@latest apply <code>`). The only custom tokens are `--status-done/doing/todo` (project step colours). Dark mode is the `dark` class set by `next-themes` (default; `ThemeRadioGroup` in the account menu of the sidebar, `ThemeToggle` on the sign-in pages).
  - Row actions (share, edit, archive, delete, move, download) are icon buttons with a tooltip: `IconButton` / `IconLink` in `src/components/actions/`. Always pass an `aria-label` with the item's name; the tooltip is only the short verb. Tooltips never open on touch (a tap runs the action), so anything a phone user has to read goes in an `InfoTip` (`src/components/actions/InfoTip.tsx`): a popover that opens on hover, focus and tap.
  - Forms keep `useActionState` + native validation (rules live in the API); `components/forms/TextField` wraps shadcn's `Field`/`Input`, `FormError` wraps `Alert`.
- UI text is in English.

## Skills (`.claude/skills/`)

Project rules in this file take precedence over any skill. A skill never authorizes `git commit` / `git push`.

- **`grilling`** (`/grill-me`) — before implementing a new feature or making an architecture decision (auth, data model, roles, API contract), grill the user on the plan first. Skip it for small fixes and obvious changes.
- **`react-best-practices`** — apply when writing, reviewing or refactoring React / Next.js code in `frontend/` (components, pages, data fetching, bundle size). Where it conflicts with the Next.js 16 docs in `node_modules/next/dist/docs/`, the docs win.
- **`shadcn`** (official, installed with `pnpm dlx skills add shadcn/ui --skill shadcn --agent claude-code --copy`; to update it, run the same command again) — apply when adding, composing or styling UI in `frontend/`: shadcn CLI usage, Base UI vs Radix, form and composition rules. Project rules here and the Next.js 16 docs take precedence over it.
- **`web-design-guidelines`** (Vercel's, installed with `pnpm dlx skills add vercel-labs/agent-skills --skill web-design-guidelines --agent claude-code --copy`; to update it, run the same command again) — apply when reviewing or auditing `frontend/` UI for accessibility, UX and Web Interface Guidelines compliance ("review my UI", "check accessibility"). It fetches the current rules from GitHub at review time, so it needs network access. A review skill: it reports findings as `file:line`, and fixes are made only when asked.
- **`frontend-design`** — apply when building a new UI or reshaping an existing one visually and no design is provided. Do not use it when a Figma design or an existing design system defines the look; follow that instead.

## VS Code (`.vscode/`)

- Launch: **API** (debugger) and **Full stack** (compound, F5: runs the `frontend` task, plain `pnpm dev` in its own terminal, then the API under the debugger). The frontend is not debugged from VS Code and keeps running when the API session stops.
- Tasks: `frontend`, `build-api`, `test` (default), `db-up`, `db-migrate`, `db-seed`. The `db-*` tasks are not tied to F5.

## Prerequisites

- Backend: .NET SDK 10, `dotnet-ef`, Docker for Postgres, Mailpit (the local email catcher) and RustFS (the local S3-compatible file storage); details in `backend/CLAUDE.md`. Frontend: Node.js + pnpm (the version is pinned in `frontend/package.json`; install with `npm install -g pnpm`; Corepack 0.31 cannot run pnpm 12).
- Works on Windows, macOS and Linux; use forward slashes and shell-agnostic commands in docs and scripts.
