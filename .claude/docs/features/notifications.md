# Notifications (stored, emailed, inbox, live push)

Details and reasons: `decisions.md`, "Notificări". The **Notifications service** (`backend/src/Services/Notifications`, database `partnr_notifications`, HTTP port 5055) owns all of it; Workspaces only says what happened.

## How a notification is born

- Workspaces decides **who** has to hear about something (only it knows who may open a project and who is still a member) and publishes an event naming them, through `INotificationPublisher` (`Application/Notifications/NotificationPublisher`), **before** its `SaveChanges`, so the event leaves exactly when its change is saved (Wolverine outbox, see `backend/CLAUDE.md`). The event carries the recipient's account id, **email and name** and the snapshot names (workspace, project, deliverable, who answered), so the Notifications service never calls back and has no accounts of its own.
- Three events: `ApprovalRequested` tells the client (the account linked to the project's card, and only if they can open the project), `ApprovalDecided` tells the member who asked, `InvitationAccepted` tells the member who invited (a member who left is skipped, and a recipient without an account is skipped). `ApprovalRequestWithdrawn` (a request taken back, its deliverable unshared or archived) marks the notification obsolete: it leaves the inbox and its email, if it has not left yet, is cancelled. `ConversationChanged` (messages) only triggers a push.
- Two more events are emails, not notifications: `ClientInvited` (an invitation) and `PasswordResetRequested`, published by Workspaces with the recipient's address and name and the **plain token** (the broker carries it; Workspaces keeps only the hash). `TransactionalEmailService` writes the text and the link (`/invite/{token}`, `/reset-password/{token}`) and sends it straight away: nothing is stored, so nothing here keeps the token. A failing send (SMTP down) is retried by Wolverine (5 s, 30 s, 2 min), then dead-lettered; a repeated event sends the same email twice, which does no harm.
- Delivery is at least once, so the service is idempotent: a notification has a `DedupeKey` (unique), and a withdrawal that arrives before its request leaves a tombstone (`WithdrawnRequest`) so the late request is dropped.

## API (Notifications service, through the gateway)

- **Inbox**: `INotificationService` behind `/api/notifications` (`GET`, `GET unread-count`, `POST {id}/read`, `POST read-all`): the account's own, across workspaces, newest 30; someone else's, an obsolete one and an unknown id are all 404. It trusts only the gateway's JWT (account id in `sub`).
- **Live push**: after a save that worked, the event service tells the recipient through `IInboxPublisher`; the Api's `SignalRInboxPublisher` sends `inboxChanged` (no data, the browser asks the REST routes) over `NotificationsHub` at `/api/hubs/notifications` (under `/api`, so the web app's rewrite and the gateway's `/api/hubs` route carry the WebSocket), to the account by id (`Clients.User`, no groups). Marking read and the email worker's own changes: read pushes, the worker pushes nothing. One instance only: more would need a backplane. A failed push is logged and never fails the request. **Needs ASP.NET Core 10.0.13 or newer in production** (GHSA-334f-vvp4-7g6p, a SignalR denial of service fixed in 10.0.13).
- **Email**: sent by `NotificationEmailWorker` through `INotificationEmailService.SendDueAsync`, to the email the event named: it claims due rows with one `UPDATE … RETURNING … FOR UPDATE SKIP LOCKED` that also pushes their next attempt 5 minutes out, retries up to 5 times (1, 5, 15, 60 minutes), then marks the row `Failed`. The `Notifications` section turns the worker off (`EmailWorkerEnabled`, off in the integration tests, which call the service themselves) or changes its pace (`EmailPollSeconds`, 5). The text is built once in `NotificationContent` (title and link only, never the user's own message). Links open `App:FrontendUrl`.
- Settings: `ConnectionStrings:Postgres`, `Email` (SMTP, Mailpit in development), `Events` (broker, `Prefix`), `InternalAuth:SigningKey`, `App:FrontendUrl`. In Development the database is created and migrated at startup.

## Web app

- The `NotificationsBell` sits in the top bar of `Page.tsx` (`src/components/notifications/`): a popover with the latest 30, a click marks one read and opens it, "Mark all as read"; its button is named "Notifications, N unread".
- The data and the SignalR connection live in `NotificationsProvider`, mounted in `AppShell` because a layout outlives page navigation: one WebSocket-only connection per tab and area, the server only says `inboxChanged` and the REST routes answer, no polling; the state reloads whenever the connection (re)starts. Messages use the same connection ([messages.md](messages.md)).
- In e2e tests a bell with no number also means "not loaded yet", so wait for a number. The notification now arrives a moment after the action (over the broker), so wait with `expect(...)` rather than reading once.

## Tests

Unit tests for the entity, the event service (who gets what, duplicates, tombstone), the inbox and the email retry rules; integration tests on a real Postgres (`tests/Notifications/Partnr.Notifications.IntegrationTests`: inbox, SignalR push over `TestServer`, and the whole trip over a RabbitMQ container); Workspaces tests check what is published (`NotificationPublisherTests`, `ConversationsOverTheBrokerTests`); e2e (`notifications.spec.ts`) runs the real chain with Mailpit.
