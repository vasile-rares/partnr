# Projects, stages and the project page

The sections inside the project page have their own files: [deliverables-and-approvals.md](deliverables-and-approvals.md), [updates.md](updates.md), [files.md](files.md).

## API

- Projects (`/api/workspaces/{id}/projects`, `?includeArchived=true&clientId=`) follow the clients' rules: members create and edit, the owner archives and restores.
- A project belongs to one client of the same workspace, chosen at creation and never changed (the update request has no `clientId`); an archived client cannot get a new one (409).
- An **archived project is read-only**: every change answers 409 until it is restored.
- The status (`Planning`, `Active`, `OnHold`, `Completed`) is set by hand and stored as text; `Planning` means the client will not see the project in the portal.
- **A stage's due date has to fall inside the project's dates** (on or after the start and on or before the due date, whichever the project has; `Project.AddStage` / `UpdateStage` throw `DomainException`, so a 400 with the reason) and the project's dates cannot move away from a dated stage (`UpdateDetails` refuses it and names the stage).
- Stages are part of the `Project` aggregate (`AddStage`/`UpdateStage`/`MoveStage`/`RemoveStage`, positions always 0, 1, 2... with no unique index on them, see the plan) and are changed through `.../projects/{id}/stages[/{stageId}[/move]]`; each call answers with the whole project, and an archived project refuses them (409).
- `ProjectResponseBuilder` names the client through `ClientResponseBuilder`, so a client with an account shows the account's name.

## Web app

- `src/app/w/[workspaceId]/projects/` (list, `[projectId]`; a new project is made in a dialog, `NewProjectDialog`, with the client preselected when opened from a client's page), components in `src/components/projects/`, data in `src/lib/projects/`.
- **Project page** (`app/w/[workspaceId]/projects/[projectId]/page.tsx`): a header row with the name, the status and an "Edit project" button on the right, the client, then `ProjectTimeline` (below) and `ProjectTabs` (`src/components/projects/`, client) with two tabs: Overview (`FirmUpdateList`, and beside it `ProjectApprovalsCard`) and "Deliverables & Files" (`FirmDeliverableList` and `FirmFileList` side by side on wide screens), each tab's content rendered on the server and handed in as `panels`.
- Editing the project (`ProjectForm`) and archiving it are in a `Sheet` (a panel over the page) that wraps the whole page, so any `SheetTrigger` inside opens it: the header button and the deadline card's "Set dates". The panel is modal: in e2e tests `openEditor(page)` (`e2e/helpers.ts`) opens it and Escape closes it before anything behind it is used.
- **Tabs**: only the open tab is mounted, so a half-filled form does not survive a tab switch. The open tab is in the address (`?tab=deliverables`, none for Overview): it is read with `useSearchParams` and changed with `window.history.replaceState`, which Next syncs with the router without asking the server. `GoToTab` is a button inside any panel that opens another tab. The page is keyed by project id, so moving to another project starts on Overview. In e2e tests click the tab first (`openTab(page, "Deliverables")`).
- **`ProjectTimeline`** sits above the tabs, so both show it: one bar for the whole project with each stage a segment laid out by its dates (`buildTimeline` in `src/lib/projects/timeline.ts`, pure and tested without a browser in `e2e/timeline.spec.ts`: widths follow the dates only when the project has a start and an end, otherwise the stages share the bar evenly; a minimum width keeps a short stage clickable), a "Today" marker, "N of M done" and the days left or overdue. "Set dates" is a `SheetTrigger` passed in as `datesAction`. The same component, read-only, sits above the tabs of the client's project page. `ProjectProgress` (the small "N of M done" under one segment per stage) is what the lists use.
- **The stages are edited on the bar itself** (there is no stage list on the page, and no way to reorder: the bar draws the stages **by due date**, `orderByDate` in `src/lib/projects/timeline.ts`, a stage without a date keeping its place in the list; the portal's stage list and `summarize` use the same order), only for the freelancer on a project that is not archived (`editable`):
  - A segment is a button (`StagePopover`, client) that opens a menu centred under it where **everything is edited in place and saved as it is left**: the name (an input styled as a title; emptying it is refused with a message), the status (a three-button control, saved at once), the due date (picked on a calendar, saved at once), the description (saved on blur) and Delete (confirmed inside the menu); every save sends the whole draft so fields never overwrite each other, and closing the menu flushes what is pending.
  - The + at the end of the bar (or "Add the first stage" on an empty one) opens `AddStageDialog`.
  - **A stage's date has to be inside the project's** (`limits` from `lib/projects/limits.ts`) and is **picked on a calendar, never typed**: `DatePicker` / `DateField` (`src/components/forms/`, a popover with shadcn's `Calendar`, i.e. `react-day-picker`) greys out and refuses the days outside the limits and stops paging at the project's first and last month, and the API refuses a date outside it too; the menu's date saves as soon as a day is picked (in e2e tests `pickDate` / `calendarDay` in `e2e/helpers.ts` find a day by `data-day`, which is the en-US date).
  - In "time" mode the edge between two stages has a `StageDateHandle` (appears on hover, always on touch) that is dragged or moved with the arrow keys (Shift: a week) to change that stage's due date, never past its neighbours' dates, saved on release (keys: 700 ms after the last press); while dragging, the part the stage gains or loses is shown hatched.
  - Every change is one request through `useStageRequest` (the API answers with the whole project) and then `router.refresh()`.
