# Backend

.NET 10 API (Clean Architecture) with PostgreSQL. Paths and commands below are relative to `backend/`. General project rules (language, commit messages, working rules) are in the root `CLAUDE.md`.

**Reference for the structure:** [Clean Architecture in .NET 10](https://codewithmukesh.com/blog/clean-architecture-dotnet/) (codewithmukesh). The backend follows this article: four layers, plain services (no CQRS / MediatR), repositories + `IUnitOfWork`, thin controllers. When adding projects, folders or dependencies, consult it so the structure does not drift.

Solution: `Partnr.slnx`.

The backend is **Core**, the main service (a modular monolith that holds the whole domain: accounts and sign-in, workspaces, clients and invitations, projects, messages, meetings), plus the small services around it that have a concrete reason to be separate (Integrations, Notifications, Storage), all behind the gateway (plan: `.claude/docs/microservices-plan.md`). Everything below that does not name another service is Core: its projects live in `src/Services/Core/` and its tests in `tests/Core/`, all named `Partnr.Core.*` (namespace included). Each other service has the same four layers in `src/Services/<Name>/`. Do not confuse the Core service with the product concept "workspace" (a freelancer's or agency's space), which is one of its features.

Folders are grouped **by role inside each layer** (not by feature); the namespace always matches the folder.


## Events (between services)

- **A service says what happened by publishing an event** (`IEventPublisher.PublishAsync`, a type from `Partnr.Contracts.Events`) **before** `IUnitOfWork.SaveChangesAsync`, like the notification writer. `IUnitOfWork` is implemented by `Infrastructure/Events/OutboxUnitOfWork`, which saves the change and, **in the same database transaction**, the event in Wolverine's outbox (tables in the `wolverine` schema of this service's own database, built at startup). Once the transaction commits Wolverine sends the event to RabbitMQ; if the save fails, the event is never sent. Do not inject `ApplicationDbContext` to save: a plain `SaveChangesAsync` on it would lose the events.
- **Wolverine over RabbitMQ with conventional routing**: one exchange per event type (`{Prefix}{Type}`) and, per consuming service, one queue (`{Prefix}{ServiceName}.{Type}`), so every service gets its own copy. A consumer is a class with a static `Handle(TheEvent, ...)` method (Wolverine finds it by convention in the Api assembly, e.g. `Api/Events/`). Settings in the `Events` section: `RabbitMqUri` (empty means nothing leaves the process, as in the integration tests), `ServiceName`, `Prefix` (the e2e run uses `e2e.` so it never shares queues with a development API).
- **Today** the events are the meetings' (`MeetingChanged`, `MeetingSyncRetryRequested`, `MeetingSynced`, `GoogleConnected`, `GoogleDisconnected`: see "How a meeting reaches Google" below) and the notifications' (`ApprovalRequested`, `ApprovalDecided`, `InvitationAccepted`, `ApprovalRequestWithdrawn`, `ConversationChanged`, `ProjectFileRemoved` (Storage deletes the bytes), and the emails with a secret link, `ClientInvited` and `PasswordResetRequested`, which carry the plain token: see the Notifications paragraph below). Events carry what the consumer needs (ids, names, times, emails), so it does not have to call back. A handler gets the use-case services from the container (Wolverine's `ServiceLocationPolicy.AlwaysAllowed`), because they are internal on purpose.
- Tests: the unit tests check what a service publishes (`FakeEventPublisher`); `tests/.../Events/MeetingsOverTheBrokerTests` runs the real trip against a RabbitMQ container, and a save that fails sends nothing (needs Docker).

## Dependency rules

```
Api            -> Application, Infrastructure
Infrastructure -> Application
Application    -> Domain
Domain         -> nothing
```

- Dependencies point inward only. Domain depends on nothing external. These rules are checked by `tests/Core/Partnr.Core.ArchitectureTests` (`LayerDependencyTests`); add a test there when a new rule is agreed.
- Application talks to the database only through repository interfaces (`IClientRepository`, one per aggregate, in `Interfaces/Repositories/`) and `IUnitOfWork`. Both are implemented in Infrastructure: `ClientRepository` (reads, `Add`/`Remove`, never saves) and `ApplicationDbContext` (`IUnitOfWork.SaveChangesAsync`). Application has no EF Core reference.
- Api does not reference types from `Infrastructure.Persistence`; it only calls `AddInfrastructure()` from the composition root.

## Conventions

- **Services per feature**: `IXService` in `Application/Interfaces/Services/`, `XService` in `Application/Services/`, registered in `Application/DependencyInjection.cs`. Services are `internal`; only the interface and DTOs are public. A use case reads/changes entities through repositories and calls `unitOfWork.SaveChangesAsync` once at the end (one transaction per use case). Services are unit-tested with hand-written fake repositories.
- **Entities** have private setters and a static factory (`Client.Register`) that enforces invariants by throwing `DomainException`. Ids are UUID v7 (`Entity` base class).
- **Errors**: expected failures are exceptions mapped to HTTP by `Api/Middleware/ApiExceptionHandler` as `ProblemDetails`. Services throw `NotFoundException` (404) / `ConflictException` (409), both `AppException`s from `Application/Exceptions/` (add a new subclass for another status code). Entities throw `DomainException` (400, `Domain/Exceptions/`) for broken invariants. Anything else becomes 500 via `UseExceptionHandler()`. Controllers stay free of error handling.
- **Input validation** with data annotations (`[Required]`, `[MaxLength]`, `[EmailAddress]`) on the request DTOs in `Application/DTOs/<Feature>/` (`XRequest` and `XResponse` side by side), validated automatically by `[ApiController]` (returns 400 `ValidationProblemDetails`). Use non-positional records with `init` properties so the attributes sit on properties. Data annotations go on DTOs only, never on entities.
- **Mapping** by hand with extension methods in `Application/Mappings/` (`WorkspaceMappings.ToResponse()`), no AutoMapper.
- **Unique-constraint violations** (Postgres `23505`) are translated to `ConflictException` inside `ApplicationDbContext.SaveChangesAsync`, so services need no try/catch for races.
- **EF mapping** with Fluent API in `Infrastructure/Persistence/Configurations/` (`IEntityTypeConfiguration<T>`), never data annotations on entities.
- Naming: plural folders for roles (`Entities/`, `Services/`, `Controllers/`), plural feature names under `DTOs/` (`DTOs/Clients/`); suffix files with their role (`ClientService`, `ClientRepository`, `ClientsController`, `ClientConfiguration`).
- Shared settings live in `Directory.Build.props` (`net10.0`, nullable, `TreatWarningsAsErrors=true`). Do not repeat them in `.csproj` files.
- **NuGet package versions only in `Directory.Packages.props`** (central package management). In `.csproj`: `<PackageReference Include="X" />`, no `Version`. The `Microsoft.OpenApi` pin in that file addresses a vulnerability (GHSA-v5pm-xwqc-g5wc) — do not remove it without checking.

## Authentication

- **The browser holds a cookie; the API trusts the gateway's JWT.** The browser's session is an ASP.NET Core Identity **cookie** (HttpOnly, SameSite=Lax, 14 days sliding), set and cleared by the sign-in routes (`register|login|logout`, password reset). On every other request the **gateway** checks that cookie (a gRPC call to `Api/Internal/SessionValidationService`, which runs the same cookie handler) and forwards the request with a one-minute `Authorization: Bearer` JWT made by the gateway (`sub` = account id). The API validates only that JWT (`AddInternalAuthentication()` from `Partnr.ServiceDefaults`, `InternalAuth:SigningKey`, issuer and audience from `Partnr.Contracts.InternalAuth`), and JwtBearer is the default scheme: **a request that carries only the cookie is a 401 on the API**, so the API must always be reached through the gateway. The gateway also passes on the `Set-Cookie` the session check produces (sliding renewal, or the removal of a cookie whose account is gone). Integration tests keep signing in with cookies because `tests/.../Gateway/GatewayEmulatorStartupFilter` plays the gateway in front of the test API; `InternalAuthTests` removes it to test the API as it really is. `AuthService` (the use cases: duplicate-email check, generic login error, mapping) is in `Application/Services/` and is unit-tested with a fake. It talks to Identity only through the `IIdentityService` port, implemented by a thin adapter in `Infrastructure/Authentication/` (`IdentityService`, plus `ApplicationUser`) on top of `UserManager`/`SignInManager`. It is a port, not a repository: Identity saves by itself and also owns passwords, lockout and the cookie. `ICurrentUser` is implemented by `Infrastructure/Authentication/CurrentUser` (reads the user id claim from `HttpContext`), registered in `AddInfrastructure()`.
- Endpoints: `POST /api/auth/register|login|logout`, `GET /api/auth/me`. Login failures are always the same 401 message (wrong password, unknown email and lockout are indistinguishable). 5 wrong passwords lock the account for 15 minutes.
- **The whole API requires login by default** (fallback policy in `Program.cs`). A public endpoint must be marked `[AllowAnonymous]`; a new controller needs no attribute to be protected.
- **The account behind the cookie is checked on every request** (by the gateway's session check, with `SecurityStampValidatorOptions.ValidationInterval = TimeSpan.Zero`; Identity's default is 30 minutes). A cookie whose account is gone (deleted, or the development database was reseeded) is then plain anonymous: a clean 401 and the cookie is cleared. Without it such a cookie counted as signed in, so some endpoints answered 200 with empty data and `/api/auth/me` threw `UnauthorizedException` from inside the service. The cost is one primary-key lookup per request. The validator would also ask for the cookie to be re-issued on every response, and a request still in flight at sign-out then revived the session with a fresh cookie; `OnValidatePrincipal` is wrapped so `ShouldRenew` stays what the cookie handler decided from the time left (see `decisions.md`, Autentificare).
- Identity's cookie handler would redirect to a login page; it is overridden to answer 401 / 403 (an API has no login page). On the API routes JwtBearer answers 401 itself.
- CORS must keep `AllowCredentials()` or the browser will not send the cookie from `localhost:3000`.
- Roles are not global: they belong to workspace memberships (`WorkspaceMember`), so `ApplicationDbContext` extends `IdentityUserContext` (no role tables).

## Authorization (workspaces)

- Everything a freelancer or agency owns lives in a **workspace**, and its routes say so: `/api/workspaces/{workspaceId}/clients/...`. Roles (`Owner`, `Member`) belong to the membership (`WorkspaceMember`), never to the account.
- **Every service that touches data inside a workspace calls `WorkspaceAccess` first** (`Application/Authorization/WorkspaceAccess.cs`): `RequireMemberAsync` or `RequireOwnerAsync`. Do not re-implement the check in a service or a controller.
- **The client's side has its own door, `ClientAccess`** (`Application/Authorization/`): a service never looks up a project, a workspace or a client card for a client on its own. "A client may open this project" is written twice, on purpose: in C# as `Project.IsOpenToClient(client)` (messages, notifications, the unit-test fakes) and in SQL as `ProjectRepository.SharedWithClient` (lists and single reads); `ClientVisibilityRuleTests` keeps the two equal. Change one, change the other.
- **A route open to both sides resolves the caller with `CallerAccess`** (a member with a role, or a client with none; anyone else gets the usual 404), as the messages and `GET /api/workspaces/{id}` do. **The default is closed**: a route that calls `WorkspaceAccess.RequireMemberAsync` answers a client with 404, and a new one is closed to clients until someone opens it on purpose. The same route then gives each side its own answer from one service (see `decisions.md`, "Portal unificat").
- **On the firm's side, a project is found through `ProjectAccess`** (`RequireProjectAsync` to read, `RequireEditableProjectAsync` to change: 404, then 409 when archived) and the rules deliverables, updates and files share (archived is read-only, only a draft is deleted) are in `ProjectContentRules`; a service keeps only what is its own.
- A non-member gets **404**, exactly like a missing workspace, so ids cannot be probed. A member doing an owner-only action gets **403** (`ForbiddenException`), since they already know the workspace exists.
- Repositories of workspace data take the `workspaceId` in every lookup (`GetByIdAsync(workspaceId, id)`), so a record of another workspace is not found even by its id.
- Clients are not members: their portal access comes from invitations (`/api/invitations/{token}`, public to the holder of the link, except `accept` which needs the invited account) and is read through the same workspace routes as the firm's (`/api/workspaces/{id}/...`, see `CallerAccess` below) and there is no `/api/portal` any more. A client never passes `WorkspaceAccess`: an account whose card is linked sees its workspaces in `GET /api/workspaces` (with the role `Client`) and its shared projects in `GET /api/workspaces/{id}/projects[/{id}]`, in its own shape (archiving the card hides both). A project is shared when `IProjectRepository.SharedWithClient` says so: the account's card is linked and not archived, the project is not archived and has left `Planning`. A draft, an archived project, another client's project and an unknown id all answer the same 404. The client has its own DTOs (`DTOs/ClientView/`), built by `ClientProjectResponseBuilder`, and the route answers each side through a `RoleResponse` (one place decides which), so nothing of the workspace's side (client card, notes, ids of cards) can reach a client by adding a field to `ProjectResponse`.
- **Each feature's routes and rules** (workspaces, clients and their invitations, projects and stages, deliverables and approvals, updates, files, notifications, messages, the Google connection, meetings and their sync, password reset, the profile, client suggestions) are in `.claude/docs/features/`, one file per feature; the map is in the root `CLAUDE.md`. Most of them repeat the same shape: members create, edit, share and delete a draft; archiving and restoring is owner-only and sets the item back to `Draft`; an archived item and everything inside an archived project is read-only (409); something of another project is a 404; the client sees only `Shared`, non-archived items, and only after the project itself was found as shared with them.
- Members cannot be added through the API yet (invitations step); integration tests add them straight to the database.

## Adding a new feature (e.g. `Projects`)

Use `Clients` as the template. Every step is needed; nothing fails at build time if the DI lines are forgotten, the app only breaks on the first request.

1. **Domain**: `Domain/Entities/Project.cs` (private setters, static factory, throws `DomainException`); enums in `Domain/Enums/`.
2. **Application**: `Interfaces/Services/IProjectService.cs`, `Services/ProjectService.cs` (`internal`, calls `WorkspaceAccess` first if the data belongs to a workspace), `Interfaces/Repositories/IProjectRepository.cs`, `Mappings/ProjectMappings.cs`, `DTOs/Projects/` (requests and responses). One repository per aggregate, not per entity.
3. **Application DI**: register `IProjectService` in `Application/DependencyInjection.cs`.
4. **Infrastructure**: `DbSet<Project>` in `ApplicationDbContext`, `Persistence/Configurations/ProjectConfiguration.cs`, `Persistence/Repositories/ProjectRepository.cs`, and register `IProjectRepository` in `Infrastructure/DependencyInjection.cs`.
5. **Migration**: `dotnet ef migrations add <Name> ...` (see Database and migrations), then review the generated file.
6. **Api**: `Controllers/ProjectsController.cs`, thin, no error handling.
7. **Tests**: service tests in `tests/Core/Partnr.Core.UnitTests/Application/` (fake repository + fake unit of work), entity tests in `Domain/`.
8. Run `dotnet build` (0 warnings) and `dotnet test`.
9. **Docs**: describe the feature's routes and rules in `.claude/docs/features/<feature>.md` and add it to the map in the root `CLAUDE.md`.

External services (email, OAuth, AI, file storage) follow the same rule as repositories: the interface lives in `Application/Interfaces/Services/`, the implementation next to its kind of service in Infrastructure (`Storage/`, ...), never in `Persistence/`.

## Database and migrations

- PostgreSQL 17 via `docker-compose.yml` (db `partnr`, port 5432, local-dev-only credentials `postgres` / `1q2w3e`). The `Postgres` connection string is in `src/Services/Core/Partnr.Core.Api/appsettings.Development.json`. To use a different Postgres (e.g. one installed locally), override it with user secrets instead of editing that file: `dotnet user-secrets set "ConnectionStrings:Postgres" "Host=...;Password=..." --project src/Services/Core/Partnr.Core.Api`.
- **Docker Compose** (`backend/docker-compose.yml`, project `partnr`): the settings (passwords, keys) come from `backend/.env`, copied from the committed `.env.example` (ignored by git; without it the same defaults apply). The values are also in the services' `appsettings.Development.json` (connection strings, broker address, storage keys), so change them in both places. Every port is bound to `127.0.0.1` (weak local credentials: nothing is reachable from the network), every image is pinned to an exact version, every service except the dashboard has a health check (`docker compose up -d --wait` returns when they are healthy), restarts are `unless-stopped`, logs rotate at 10 MB x 3, and the data lives in the named volumes `partnr-postgres-data` and `partnr-rustfs-data`. The telemetry dashboard is the `observability` profile, turned on by `COMPOSE_PROFILES` in `.env`.
- **Email** is the Notifications service's: Core has no SMTP and sends nothing itself, it publishes an event (`ClientInvited`, `PasswordResetRequested`) and Notifications sends the email through its `IEmailSender` (`Infrastructure/Email/SmtpEmailSender`, MailKit), configured by its `Email` section (`From`, `SmtpHost`, `SmtpPort`, `SmtpUsername`, `SmtpPassword`, `UseTls`), validated at startup. In development the SMTP server is **Mailpit** from `docker-compose.yml` (SMTP on 1025, inbox UI on http://localhost:8025): every email is caught there, none reaches a real inbox. Production only changes the configuration. Core integration tests see what was published through `RecordedEmailEvents` (`ApiFactory.Emails`); `tests/Notifications/.../Email/SmtpEmailSenderTests` checks the real sender against a Mailpit container.
- **File storage** is the Storage service's (see its paragraph below). Core keeps the rules and the rows (`ProjectFile`) and reaches the bytes through `IFileStorage` (Application), implemented by `Infrastructure/Storage/GrpcFileStorage` over gRPC, address `Services:Storage:GrpcAddress`: `SaveAsync` streams the file in 64 KB chunks, `OpenReadAsync` returns a stream over the chunks (a missing file is a `NotFoundException` before the response starts), `DeleteAsync` is best effort (used only to undo an upload whose row failed to save); a Storage that cannot be reached is a 503 (`ServiceUnavailableException`). Deleting a file publishes `ProjectFileRemoved` before the save, and Storage removes the bytes, retrying until it works. Integration tests replace the storage with `InMemoryFileStorage` (`ApiFactory.Files`) and read what was published through `ApiFactory.Recorded`.
- Migrations are created in Infrastructure, started from Api (commands work in any shell):

```bash
dotnet ef migrations add <Name> --project src/Services/Core/Partnr.Core.Infrastructure --startup-project src/Services/Core/Partnr.Core.Api --output-dir Persistence/Migrations
dotnet ef database update --project src/Services/Core/Partnr.Core.Infrastructure --startup-project src/Services/Core/Partnr.Core.Api
```

**Gateway** (`src/Partnr.Gateway`, tests in `tests/Gateway/`): a YARP reverse proxy and the only entry point to the backend. It forwards `/api/integrations/*` to the Integrations service, `/api/notifications/*` and `/api/hubs/*` (the SignalR WebSocket) to the Notifications service and the rest of `/api/*` to the Core API (routes and destinations in `appsettings.json`, under `ReverseProxy`; override an address with `ReverseProxy__Clusters__<cluster>__Destinations__api__Address`). On every request that carries the session cookie (`Sessions/SessionMiddleware`) it asks the API over gRPC (`Services:Core:GrpcAddress`, `Sessions/GrpcSessionValidator`) whether the cookie is good, and if so adds `Authorization: Bearer <JWT>` (one minute, signed with `InternalAuth:SigningKey`, claim `sub` = account id; `Sessions/InternalTokenIssuer`). An `Authorization` header from the caller is always dropped. If the API cannot be asked the answer is 503, not "signed out". The API accepts only that JWT (see Authentication below). The gateway also passes on the `Set-Cookie` of the session check (renewal, removal). It holds no business logic and references no service project, only `Partnr.Contracts` and `Partnr.ServiceDefaults`.

**ServiceDefaults** (`src/BuildingBlocks/Partnr.ServiceDefaults`): what every service starts with, and nothing of business: `AddServiceDefaults()` (OpenTelemetry for logs, metrics and traces, including the Wolverine and Npgsql sources; exported over OTLP only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, which the F5 profiles do, pointing at the telemetry dashboard below; and a health check), `MapDefaultEndpoints()` (`/health`, open to anyone, served by each service itself: the gateway does not forward it) and the internal JWT (`AddInternalAuthOptions()` for the key, `AddInternalAuthentication()` for validating it). A new service calls these in its `Program.cs` instead of writing its own. No retries or circuit breakers yet: they come with the second synchronous caller between services.

**Telemetry dashboard** (`aspire-dashboard` in `docker-compose.yml`, the standalone Aspire dashboard, UI at http://localhost:18888 without login, local only): shows the logs, the metrics and one trace per request across the gateway, the gRPC calls and the services, every service under its project name (`Partnr.Core.Api`, `Partnr.Gateway`, ...). Each service exports to it over OTLP (:4317) when `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317` is set: the F5 profiles in `.vscode/launch.json` set it; for `dotnet run` set it in the terminal. Without the variable nothing is exported and the services run as before. It keeps what it shows in memory, so it starts empty after a restart.

**Integrations** (`src/Services/Integrations`, tests in `tests/Integrations/`): the second service, with the same four layers (`Partnr.Integrations.*`), its own database `partnr_integrations` (created and migrated at startup in Development only; elsewhere the migrations are a deployment step), HTTP port 5053 and gRPC port 5054. It owns everything that talks to an external provider, today Google: the connection of an account (`/api/integrations/google`, which the gateway routes to it: connect, callback, status, disconnect; the refresh tokens, `SecretProtector`, the OAuth client) and the **meeting sync queue**. Its settings are the old Core ones (`Google:*`; the credentials go in its own user secrets: `dotnet user-secrets set "Google:ClientId" "..." --project src/Services/Integrations/Partnr.Integrations.Api`, same for `Google:ClientSecret`; `Google:Fake` is Development only). It trusts only the gateway's JWT (account id in `sub`), has no cookie, no Identity and no foreign keys to accounts (they live in another service).

**Notifications** (`src/Services/Notifications`, tests in `tests/Notifications/`): the third service, the same four layers (`Partnr.Notifications.*`), its own database `partnr_notifications` (created and migrated at startup in Development only), HTTP port 5055, no gRPC. It owns the **inbox** (`/api/notifications`, which the gateway routes to it), the **email worker** (`NotificationEmailWorker`, SMTP, retries 1, 5, 15 and 60 minutes, 5 tries) and the **live push** (`NotificationsHub` at `/api/hubs/notifications`, routed by the gateway too: SignalR `inboxChanged` and `conversationChanged`, no data). It makes notifications only from events (`Api/Events/NotificationEventHandlers`): `ApprovalRequested`, `ApprovalDecided` and `InvitationAccepted` carry the recipient's account id, email and name and the snapshot names, so it has no accounts and never calls back; `ApprovalRequestWithdrawn` marks one obsolete; `ConversationChanged` only pushes; `ClientInvited` and `PasswordResetRequested` (`TransactionalEmailService`) are sent at once, not stored, and Wolverine retries a failed send (5 s, 30 s, 2 min) before dead-lettering. Delivery is at least once, so it is idempotent (unique `DedupeKey`; a withdrawal that arrives first leaves a tombstone). Core decides who is told (`INotificationPublisher`) and publishes before `SaveChanges`. It trusts only the gateway's JWT. Its settings: `Email`, `Events`, `App:FrontendUrl`, `Notifications` (`EmailWorkerEnabled`, `EmailPollSeconds`), `InternalAuth`. Details: `.claude/docs/features/notifications.md`.

**Storage** (`src/Services/Storage`, tests in `tests/Storage/`): the fourth service, the same four layers (`Partnr.Storage.*`), its own database `partnr_storage` (created and migrated at startup in Development only), HTTP port 5056 (only `/health`) and gRPC port 5057. It holds the **bytes** of every file and nothing about who may see them: it has no REST routes, no gateway route, no JWT and no accounts, its only callers are other services on the internal gRPC port (which must not be reachable from outside, like the others). `Files` (`storage.proto`): `Save` (client stream: a header with the key and content type, then chunks; saving under an existing key replaces it), `Read` (server stream, straight from the object store, so it also serves objects that predate its database) and `Delete`. A save is held in memory (at most 25 MB, `StorageLimits`: a larger one is `InvalidArgument`), hashed (SHA-256) and put in the bucket, and a `stored_files` row keeps what is known about it (key, size, content type, checksum). The object store is any S3-compatible service (`IBlobStore`, `Blobs/S3BlobStore`, AWSSDK.S3), configured by the `Storage` section here (`ServiceUrl`, `Region`, `Bucket`, `AccessKey`, `SecretKey`, `ForcePathStyle`, `CreateBucketIfMissing`), validated at startup: AWS S3, R2 or B2 in production (only the configuration changes, and the bucket is made ahead, with credentials that cannot create it); in development **RustFS** from `docker-compose.yml` (S3 API on http://localhost:9000, console on http://localhost:9001, dev credentials `rustfsadmin`/`rustfsadmin`, bucket `partnr` created on first use; MinIO no longer publishes images). It consumes `ProjectFileRemoved` (`Api/Events/`), deleting the object and its row; a failure is retried by Wolverine (5 s, 30 s, 2 min) before the dead-letter queue, and deleting twice is harmless. Tests: unit (service and entity), architecture, integration (`S3BlobStoreTests` against a RustFS container, `FilesGrpcTests` over gRPC with Postgres and an in-memory object store, `ProjectFileRemovedOverTheBrokerTests` with RabbitMQ). Details: `.claude/docs/features/files.md`.

**How a meeting reaches Google** (the whole trip, all through events): `MeetingService` (Core) asks Integrations over gRPC whether the organiser is connected when it creates a meeting (409 "Connect your Google account first", **503 if Integrations cannot be reached**), then publishes `MeetingChanged` with everything the calendar needs (title, times, the client's email, the organiser, the version, whether it is cancelled) on every schedule, change and cancel. Integrations takes it into its queue (`meeting_syncs`: the row is the queue; an event that is not newer than the row, a repeat or one that arrives late, changes nothing), and its worker (`MeetingSyncWorker`, `Google:SyncPollSeconds`, claim with `FOR UPDATE SKIP LOCKED`, backoff 1, 5, 15 and 60 minutes, 5 tries) brings the event in Google to the newest version, then publishes `MeetingSynced` (`Synced`, `Failed` or `NeedsReconnect`, only final answers, with the version it is about and the Meet link). Core applies it to the meeting it is about unless the meeting moved on (`Meeting.ApplySyncResult`: `SyncStatus` and `MeetUrl` are all that is kept there). `POST …/retry-sync` publishes `MeetingSyncRetryRequested`. Connecting or disconnecting Google publishes `GoogleConnected` / `GoogleDisconnected`, which put the organiser's waiting meetings back in the queue or park them (on both sides). Handlers live in `Api/Events/` of each service.

**gRPC (internal)**: the API (5052) and the Integrations service (5054) each have a second Kestrel endpoint for gRPC, HTTP/2 only (cleartext HTTP/2 needs its own port): `Kestrel:Endpoints` in `appsettings.Development.json` defines both `Http` (5051) and `Grpc` (5052), and because they are defined there `ASPNETCORE_URLS` is ignored. The port is internal: the gateway does not route to it and it must not be reachable from outside. Contracts (`.proto` files and the shape of the internal JWT) live in `src/BuildingBlocks/Partnr.Contracts`, which has no logic. The gRPC service sits next to the controllers in `Api/Internal/` and is `[AllowAnonymous]` because its caller is the one asking for proof. The Integrations one answers `GoogleConnections.GetStatus` (is this account connected?), which Core asks when a meeting is created; it is open to anyone who reaches the port, so the same rule applies.

- **Test data (development only):** `-- --seed` (VS Code task `db-seed`) applies pending migrations and adds demo accounts, workspaces and clients, then exits. It is never automatic, so the e2e and integration databases stay empty. It is safe to run again: when `demo@example.com` exists it does nothing. **F5 ("API" launch profile) reseeds on its own when the seed changed**: it sets `Seed__ReseedOnChange=true`, and at startup the API compares a fingerprint of the seed's source (`SeedFingerprint`: `DevelopmentSeed.cs` and `DevelopmentDataSeeder.cs`, embedded in the assembly at build) with the one stored as the database's own comment (`COMMENT ON DATABASE`, no table). If they differ, or the database has demo data but no fingerprint, **every table is dropped (`DROP SCHEMA public CASCADE`), recreated by the migrations and seeded again, so anything entered by hand is lost**; it refuses a database that is not on localhost. It is off by default because the integration and e2e runs are in Development too; `dotnet run` without that variable never recreates anything (use `-- --seed` by hand). Seeding writes files to the storage, so RustFS must be running. Stop the running API first (a debugger locks the DLLs `dotnet run` has to rebuild). The accounts (`demo@example.com`, password `demo-password`, and others) and everything the seed creates are listed in `.claude/docs/features/seed-data.md`; keep that list in step with `DevelopmentDataSeeder.cs`.

- API docs (Development only): Scalar at `http://localhost:5050/scalar/v1`, spec at `/openapi/v1.json`, both **through the gateway** (a Development-only route in its `appsettings.Development.json` that passes the original Host on, so the spec names the gateway as the server). Sign in to the web app first: the browser sends its session cookie to any port of `localhost`, the gateway turns it into the JWT, and "Try it" works on authenticated routes. On `:5051` the docs load but authenticated calls are a 401.
- CORS allows `http://localhost:3000` (frontend).
- Before saying a change is done: `dotnet build` with zero warnings and a green `dotnet test`.
