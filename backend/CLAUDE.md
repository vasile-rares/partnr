# Backend

.NET 10 API (Clean Architecture) with PostgreSQL. Paths and commands below are relative to `backend/`. General project rules (language, commit messages, working rules) are in the root `CLAUDE.md`.

**Reference for the structure:** [Clean Architecture in .NET 10](https://codewithmukesh.com/blog/clean-architecture-dotnet/) (codewithmukesh). The backend follows this article: four layers, plain services (no CQRS / MediatR), repositories + `IUnitOfWork`, thin controllers. When adding projects, folders or dependencies, consult it so the structure does not drift.

Solution: `Partnr.slnx`.

Folders are grouped **by role inside each layer** (not by feature); the namespace always matches the folder.


## Dependency rules

```
Api            -> Application, Infrastructure
Infrastructure -> Application
Application    -> Domain
Domain         -> nothing
```

- Dependencies point inward only. Domain depends on nothing external. These rules are checked by `tests/Partnr.ArchitectureTests` (`LayerDependencyTests`); add a test there when a new rule is agreed.
- Application talks to the database only through repository interfaces (`IClientRepository`, one per aggregate, in `Interfaces/Repositories/`) and `IUnitOfWork`. Both are implemented in Infrastructure: `ClientRepository` (reads, `Add`/`Remove`, never saves) and `ApplicationDbContext` (`IUnitOfWork.SaveChangesAsync`). Application has no EF Core reference.
- Api does not reference types from `Infrastructure.Persistence`; it only calls `AddInfrastructure()` from the composition root.

## Conventions

- **Services per feature**: `IXService` in `Application/Interfaces/Services/`, `XService` in `Application/Services/`, registered in `Application/DependencyInjection.cs`. Services are `internal`; only the interface and DTOs are public. A use case reads/changes entities through repositories and calls `unitOfWork.SaveChangesAsync` once at the end (one transaction per use case). Services are unit-tested with hand-written fake repositories.
- **Entities** have private setters and a static factory (`Client.Register`) that enforces invariants by throwing `DomainException`. Ids are UUID v7 (`Entity` base class).
- **Errors**: expected failures are exceptions mapped to HTTP by `Api/Middleware/ApiExceptionHandler` as `ProblemDetails`. Services throw `NotFoundException` (404) / `ConflictException` (409), both `AppException`s from `Application/Exceptions/` (add a new subclass for another status code). Entities throw `DomainException` (400, `Domain/Exceptions/`) for broken invariants. Anything else becomes 500 via `UseExceptionHandler()`. Controllers stay free of error handling.
- **Input validation** with data annotations (`[Required]`, `[MaxLength]`, `[EmailAddress]`) on the request DTOs in `Application/DTOs/<Feature>/` (`XRequest` and `XResponse` side by side), validated automatically by `[ApiController]` (returns 400 `ValidationProblemDetails`). Use non-positional records with `init` properties so the attributes sit on properties. Data annotations go on DTOs only, never on entities.
- **Mapping** by hand with extension methods in `Application/Mappings/` (`WorkspaceMappings.ToResponse()`), no AutoMapper.
- **Unique-constraint violations** (Postgres `23505`) are translated to `ConflictException` inside `ApplicationDbContext.SaveChangesAsync`, so services need no try/catch for races.
- **EF mapping** with Fluent API in `Infrastructure/Persistence/Configurations/` (`IEntityTypeConfiguration<T>`), never data annotations on entities.
- Naming: plural folders for roles (`Entities/`, `Services/`, `Controllers/`), plural feature names under `DTOs/` (`DTOs/Clients/`); suffix files with their role (`ClientService`, `ClientRepository`, `ClientsController`, `ClientConfiguration`).
- Shared settings live in `Directory.Build.props` (`net10.0`, nullable, `TreatWarningsAsErrors=true`). Do not repeat them in `.csproj` files.
- **NuGet package versions only in `Directory.Packages.props`** (central package management). In `.csproj`: `<PackageReference Include="X" />`, no `Version`. The `Microsoft.OpenApi` pin in that file addresses a vulnerability (GHSA-v5pm-xwqc-g5wc) — do not remove it without checking.

## Authentication

- **ASP.NET Core Identity** with a **cookie** (HttpOnly, SameSite=Lax, 14 days sliding), no JWT. `AuthService` (the use cases: duplicate-email check, generic login error, mapping) is in `Application/Services/` and is unit-tested with a fake. It talks to Identity only through the `IIdentityService` port, implemented by a thin adapter in `Infrastructure/Authentication/` (`IdentityService`, plus `ApplicationUser`) on top of `UserManager`/`SignInManager`. It is a port, not a repository: Identity saves by itself and also owns passwords, lockout and the cookie. `ICurrentUser` is implemented by `Infrastructure/Authentication/CurrentUser` (reads the user id claim from `HttpContext`), registered in `AddInfrastructure()`.
- Endpoints: `POST /api/auth/register|login|logout`, `GET /api/auth/me`. Login failures are always the same 401 message (wrong password, unknown email and lockout are indistinguishable). 5 wrong passwords lock the account for 15 minutes.
- **The whole API requires login by default** (fallback policy in `Program.cs`). A public endpoint must be marked `[AllowAnonymous]`; a new controller needs no attribute to be protected.
- **The account behind the cookie is checked on every request** (`SecurityStampValidatorOptions.ValidationInterval = TimeSpan.Zero`; Identity's default is 30 minutes). A cookie whose account is gone (deleted, or the development database was reseeded) is then plain anonymous: a clean 401 and the cookie is cleared. Without it such a cookie counted as signed in, so some endpoints answered 200 with empty data and `/api/auth/me` threw `UnauthorizedException` from inside the service. The cost is one primary-key lookup per request. The validator would also ask for the cookie to be re-issued on every response, and a request still in flight at sign-out then revived the session with a fresh cookie; `OnValidatePrincipal` is wrapped so `ShouldRenew` stays what the cookie handler decided from the time left (see `decisions.md`, Autentificare).
- Identity's cookie handler would redirect to a login page; it is overridden to answer 401 / 403 (an API has no login page).
- CORS must keep `AllowCredentials()` or the browser will not send the cookie from `localhost:3000`.
- Roles are not global. They will belong to workspace memberships (next step), so `ApplicationDbContext` extends `IdentityUserContext` (no role tables).
- **Password reset** (`PasswordResetService`, `PasswordResetToken`, table `password_reset_tokens`): `POST /api/auth/forgot-password` always answers 204 and emails only an existing account, through `IBackgroundEmailQueue` (in memory, so the response time does not show whether an email went out); the link carries a `SecureToken` (only its hash is stored, as for invitations), works once, for an hour, and a newer link cancels it; one email a minute per account and a global rate limit (`RateLimitPolicies.PasswordReset`; per address is pointless while the web app's proxy hides the visitor's address). `GET /api/auth/reset-password/{token}` checks a link (404 not ours, 409 used / replaced / expired); `POST /api/auth/reset-password` sets the password through `IIdentityService.ResetPasswordAsync` (same password rules, lockout cleared, security stamp changed, so every other session is signed out) and signs this one in. Email confirmation is not built.

## Authorization (workspaces)

- Everything a freelancer or agency owns lives in a **workspace**, and its routes say so: `/api/workspaces/{workspaceId}/clients/...`. Roles (`Owner`, `Member`) belong to the membership (`WorkspaceMember`), never to the account.
- **Every service that touches data inside a workspace calls `WorkspaceAccess` first** (`Application/Authorization/WorkspaceAccess.cs`): `RequireMemberAsync` or `RequireOwnerAsync`. Do not re-implement the check in a service or a controller.
- A non-member gets **404**, exactly like a missing workspace, so ids cannot be probed. A member doing an owner-only action gets **403** (`ForbiddenException`), since they already know the workspace exists.
- Repositories of workspace data take the `workspaceId` in every lookup (`GetByIdAsync(workspaceId, id)`), so a record of another workspace is not found even by its id.
- Clients are not members: their portal access comes from invitations (`/api/invitations/{token}`, public to the holder of the link, except `accept` which needs the invited account) and is read through `/api/portal/...`, which is about the signed-in account itself and so has no workspace in the route. A client never passes `WorkspaceAccess`: an account whose card is linked sees its workspaces' names in `GET /api/portal/workspaces` and its shared projects in `GET /api/portal/projects[/{id}]` (archiving the card hides both). A project is shared when `IProjectRepository.SharedWithClient` says so: the account's card is linked and not archived, the project is not archived and has left `Planning`. A draft, an archived project, another client's project and an unknown id all answer the same 404. The portal has its own DTOs (`DTOs/Portal/`), so nothing of the workspace's side (client card, notes, ids of cards) can reach a client by adding a field to `ProjectResponse`.
- The account profile (`PUT /api/auth/me`: full name, phone, company) is the user's own; the email is not part of it and cannot be changed yet. The phone is Identity's `PhoneNumber` column.
- Clients: any member adds and edits them and sees all of them; **archiving and restoring is owner-only** (`RequireOwnerAsync`).
- Projects (`/api/workspaces/{id}/projects`, `?includeArchived=true&clientId=`) follow the same rules: members create and edit, the owner archives and restores. A project belongs to one client of the same workspace, chosen at creation and never changed (the update request has no `clientId`); an archived client cannot get a new one (409). An **archived project is read-only**: every change answers 409 until it is restored. The status (`Planning`, `Active`, `OnHold`, `Completed`) is set by hand and stored as text; `Planning` means the client will not see the project in the portal. **A stage's due date has to fall inside the project's dates** (on or after the start and on or before the due date, whichever the project has; `Project.AddStage` / `UpdateStage` throw `DomainException`, so a 400 with the reason) and the project's dates cannot move away from a dated stage (`UpdateDetails` refuses it and names the stage). Stages are part of the `Project` aggregate (`AddStage`/`UpdateStage`/`MoveStage`/`RemoveStage`, positions always 0, 1, 2... with no unique index on them, see the plan) and are changed through `.../projects/{id}/stages[/{stageId}[/move]]`; each call answers with the whole project, and an archived project refuses them (409). `ProjectResponseBuilder` names the client through `ClientResponseBuilder`, so a client with an account shows the account's name.
- Deliverables (`/api/workspaces/{id}/projects/{projectId}/deliverables`, `?includeArchived=true`) are their own aggregate (`Deliverable`, `IDeliverableRepository`), tied to a project and optionally to one of its stages (deleting the stage only clears the link, `ON DELETE SET NULL`). The link must be `https` (checked in the entity). `Draft` / `Shared` is set by hand; the client sees only `Shared`, non-archived ones, inside `GET /api/portal/projects/{id}` (`deliverables`, `PortalDeliverableResponse`; `IDeliverableRepository.ListSharedAsync` runs only after the project itself was found as shared with the client, so a draft or archived project hides its deliverables too). Members create, edit, share and delete a draft (a shared one answers 409); **archiving and restoring is owner-only**, archiving also sets the status back to `Draft`. An archived deliverable and every deliverable of an archived project are read-only (409). A stage or deliverable of another project is a 404.
- Approvals are rounds (`ApprovalRequest`, `IApprovalRequestRepository`, never removed): a member asks for one on a `Shared` deliverable (`POST .../deliverables/{id}/approvals` with an optional `note`, 409 on a draft, an archived deliverable or while one is `Pending`; `.../approvals/{approvalId}/withdraw` takes it back), and a partial unique index allows only one `Pending` round per deliverable. `DeliverableResponse` carries `approvalStatus` (`None`, `Pending`, `Approved`, `ChangesRequested`: the latest round that was not withdrawn) and every round newest first in `approvals`, built by `DeliverableResponseBuilder`. An open round **freezes the deliverable's details** (update answers 409); `unshare` and `archive` **withdraw** it; a deliverable with any round in its history **cannot be deleted** (409, archive it). The client answers through `POST /api/portal/projects/{projectId}/deliverables/{deliverableId}/approvals/{approvalId}/approve|request-changes` (`PortalApprovalService`; body `message`, optional on approve, **required** on request-changes; the answer is the updated `PortalDeliverableResponse`). It goes through the same door as reading the project (`GetSharedWithClientAsync`), so a draft or archived project, someone else's project, an unshared or archived deliverable and an unknown round are all 404, and a round that is no longer open (answered or withdrawn) is a 409; a decision is final. The portal's `PortalDeliverableResponse` carries `approval` (`status`, the open round as `pending` with its note, and the decided rounds as `history` newest first; **withdrawn rounds never show**, and no ids or accounts), and projects carry `awaitingApproval` (the list and the single project), counting only pending rounds on deliverables the client can see (`IApprovalRequestRepository.CountPendingForClientAsync`). The freelancer's `ProjectResponse` carries `approvals` (`pending`, `changesRequested`, both counted by deliverable from its latest round that was not withdrawn, shared and non-archived deliverables only), filled for the whole list in one query by `ProjectResponseBuilder` (`IApprovalRequestRepository.CountForProjectsAsync`).
- Project updates, the timeline's written notes (`/api/workspaces/{id}/projects/{projectId}/updates`, `?includeArchived=true`), are their own aggregate (`ProjectUpdate`, `IProjectUpdateRepository`) with a `Title` and an optional plain-text `Body`, and follow the deliverables' rules exactly: `Draft` / `Shared` by hand, members create, edit, share and delete a draft (a shared one answers 409), archive and restore are owner-only and archiving sets the status back to `Draft`, an archived update and every update of an archived project are read-only (409) but can be read, another project's update is a 404. `SharedAtUtc` is set on the first share and kept; the list the freelancer reads is newest created first. The client sees only `Shared`, non-archived ones inside `GET /api/portal/projects/{id}` (`updates`, `PortalProjectUpdateResponse`: id, title, body and the share date only, most recently shared first; `IProjectUpdateRepository.ListSharedAsync` runs only after the project itself was found as shared with the client). There is no automatic event log; see the plan's ideas.
- Project files (`/api/workspaces/{id}/projects/{projectId}/files`, `?includeArchived=true`) are their own aggregate (`ProjectFile`, `IProjectFileRepository`, `ProjectFileService`), separate from deliverables and with no approvals. `POST` takes multipart (`file`, optional `name` and `description`); the bytes go to `IFileStorage` under a key made of ids only (`{workspaceId}/{projectId}/{fileId}`), written **before** the row and deleted **after** the row on delete (best-effort, an orphan is the worst case). The entity enforces the rules (`DomainException`, 400): at most 25 MB, not empty, an allow-list of extensions (checked by extension only; the served content type comes from it, never from the browser). `GET {id}/download` is always an `attachment` with `nosniff` and `Content-Length` (`ControllerBaseExtensions.DownloadFile`). It follows the deliverables' rules otherwise: `Draft` / `Shared` by hand, members upload, edit (name and description; the file is never replaced), share and delete a draft (a shared one answers 409), archive and restore are owner-only and archiving sets the status back to `Draft`, an archived file and every file of an archived project are read-only (409) but can be read and downloaded, another project's file is a 404. The client sees only `Shared`, non-archived ones inside `GET /api/portal/projects/{id}` (`files`, `PortalProjectFileResponse`: id, name, description, fileName and sizeBytes only; `IProjectFileRepository.ListSharedAsync` runs only after the project was found as shared with the client) and downloads through `GET /api/portal/projects/{projectId}/files/{fileId}/download` (`PortalService.DownloadFileAsync`, the same door; a draft, retracted or archived file, a project in Planning or archived and someone else's project all answer 404).
- Notifications (step a: stored, emailed; the inbox and SignalR come next) are rows of `Notification` (`INotificationRepository`), written by the services through `INotificationWriter` **before** their `SaveChanges`, so a notification exists exactly when its change does. Three events: a request for approval tells the client (the account linked to the project's card, and only if they can open the project), the client's answer tells the member who asked, an accepted invitation tells the member who invited (a member who left is skipped). Withdrawing a request, unsharing or archiving its deliverable marks its notification obsolete (`ApprovalRequestWithdrawnAsync`): it leaves the inbox and the email, if it has not left yet, is cancelled. The inbox (step b) is `INotificationService` behind `/api/notifications` (`GET`, `GET unread-count`, `POST {id}/read`, `POST read-all`): the account's own, across workspaces, newest 30; someone else's, an obsolete one and an unknown id are all 404. **Live push (step c):** after a save that worked, `InboxPushInterceptor` (an EF `SaveChangesInterceptor`) finds the accounts whose notifications were added, read or made obsolete and tells them through `IInboxPublisher`; the Api's `SignalRInboxPublisher` sends `inboxChanged` (no data, the browser asks the REST routes) over `NotificationsHub` at `/api/hubs/notifications` (under `/api`, so the web app's rewrite carries the WebSocket), to the account by id (`Clients.User`, no groups). The email worker's own changes push nothing. One API instance only: more would need a backplane. A failed push is logged and never fails the request. **Needs ASP.NET Core 10.0.13 or newer in production** (GHSA-334f-vvp4-7g6p, a SignalR denial of service fixed in 10.0.13). The email is sent by `NotificationEmailWorker` through `INotificationEmailService.SendDueAsync`: it claims due rows with one `UPDATE … RETURNING … FOR UPDATE SKIP LOCKED` that also pushes their next attempt 5 minutes out, retries up to 5 times (1, 5, 15, 60 minutes), then marks the row `Failed`. The `Notifications` section turns the worker off (`EmailWorkerEnabled`, off in the integration tests, which call the service themselves) or changes its pace (`EmailPollSeconds`, 5). The text is built once in `NotificationContent` (title and link only, never the user's own message). Details in the plan's `decisions.md`, "Notificări".
- **Messages** (one conversation per project, `Message` and `ConversationRead`): the firm reaches them through `MessageService` (`/api/workspaces/{id}/conversations`, members) and the client through `PortalMessageService` (`/api/portal/workspaces/{id}/conversations`, the portal's door); both hand over to `Messaging/ConversationThreads`. A conversation exists only while the client can open the project (`ConversationThreads.IsOpen`, the portal's rule), otherwise 404. Plain text up to 4000 characters; the author edits or deletes within 10 minutes (403 for someone else, 409 after or once deleted; a deleted message loses its text and keeps its place). Read marks are per person, set from the id of the newest message shown and never moved back. Changes push `conversationChanged` with the project id over the notifications hub (`IConversationPublisher`). Details in `decisions.md`, "Mesaje".
- **Google connection** (step 1 of Meetings; `GoogleConnection`, table `google_connections`, one per account): the person's own permission to use their Google Calendar, so no workspace in the route (`/api/integrations/google`: `GET` status, `POST connect` answers `{ url }` for Google's consent page, `GET callback` where Google sends the browser back, `DELETE`). `GoogleConnectionService` + the `IGoogleOAuthClient` port (Infrastructure `Google/GoogleOAuthClient`, plain `HttpClient`, no Google SDK) + `ISecretProtector`. The callback goes through the web app's `/api/*` rewrite (the redirect URI is `http://localhost:3000/api/integrations/google/callback`) so the session cookie comes along, and always ends in a 302 to `/account?google=connected|denied|permission|error`: expected failures are a `GoogleConnectOutcome`, never an exception. **The state is `ISecretProtector.Protect` of `userId|expiry`** (10 minutes): bound to the account, so a link made for someone else cannot connect their Google to this account. The scope is `calendar.events` (plus `openid email` to show which account); the person can untick it on Google's screen, which is `MissingPermission`. Only the **refresh token** is kept, encrypted (`SecretProtector`: AES-256-GCM, key from `Google:EncryptionKey`, the purpose is authenticated data) and never returned by the API; disconnecting revokes it at Google (best effort) and deletes the row. The Google features are off while `Google:ClientId` / `ClientSecret` are empty (`Available: false`, `POST connect` answers 409), and the options check at startup rejects a bad key or redirect only when they are set. Set up locally: create an OAuth client (type "Web application") in Google Cloud with that redirect URI and the `calendar.events` scope, then `dotnet user-secrets set "Google:ClientId" "..." --project src/Partnr.Api` and the same for `Google:ClientSecret`; the dev `EncryptionKey` is in `appsettings.Development.json` (make a real one with `openssl rand -base64 32` for production). Integration tests replace the Google client with `FakeGoogleOAuthClient` (`ApiFactory.Google`). **`Google:Fake=true`** swaps both Google clients for stand-ins (`Infrastructure/Google/FakeGoogle.cs`): the consent screen is skipped (the browser goes straight to the callback with `code=fake-ok`; `fake-no-calendar` is an unticked calendar), every event gets a Meet link, and a meeting titled with `[google-down]` fails. It is for the browser tests (`e2e/start-api.mjs` sets it) and **the options check refuses it outside Development**.
- **Meetings** (`Meeting`, table `meetings`, `MeetingService`, `PortalMeetingService`; sent to Google by the sync below): `/api/workspaces/{id}/meetings` (`POST`, `GET ?includeCancelled=&clientId=&projectId=` soonest first, `GET {id}`, `PUT {id}`, `POST {id}/cancel`; members, no owner-only action) and the client's read-only `GET /api/portal/workspaces/{id}/meetings`. A meeting has a client (required, never changed), an optional project (of that client, not archived, 409 otherwise) and an **organiser**, the member who created it, fixed for good: any member may edit or cancel it, but its Google event will live in the organiser's calendar. **Creating needs the creator's own Google connection to be `Connected`** (409 "Connect your Google account first"); editing and cancelling do not, so a lapsed account cannot lock a meeting. There is no draft. The request carries `DateTimeOffset startsAt` / `endsAt` (stored as UTC); a meeting lasts 5 minutes to 8 hours, and a new or moved one has to start in the future (400), while title, note and project can still be fixed while it runs. A cancelled meeting and one that already ended are history: update and cancel answer 409, and `Cancel` keeps the row. An archived client or project blocks scheduling and editing (409). The client sees only meetings of its own linked, non-archived card (an archived card closes the whole firm's portal door, 404, like for projects), cancelled ones included for 30 days, with the project named **only when the client can open it** (`ListSharedWithClientAsync`: a Planning project is never named); no organiser, no client card (`PortalMeetingResponse`). Foreign keys are `Restrict`, as everywhere: a meeting is history.
- **Meeting sync** (step 3 of Meetings; `MeetingSyncService`, `MeetingSyncWorker`, `IGoogleCalendarClient` implemented by Infrastructure `Google/GoogleCalendarClient`, plain `HttpClient` like the OAuth client). **The meeting row is the queue**: `SyncStatus` (`Pending`, `Synced`, `Failed`, `NeedsReconnect`), `SyncAttempts`, `NextSyncAtUtc`, `Version`, `GoogleEventId`, `MeetUrl`. Every change (schedule, update, cancel) bumps `Version` and makes the meeting `Pending` and due now, so the sync always brings Google to what the meeting says *now*, whatever happened in between. `MeetingSyncWorker` (a `BackgroundService`, every `Google:SyncPollSeconds` = 5 s, `Google:SyncWorkerEnabled`, off while `Google:ClientId` is empty and in the integration tests, which call `IMeetingSyncService.SyncDueAsync` themselves) claims due rows with one `UPDATE … RETURNING … FOR UPDATE SKIP LOCKED` that also pushes their next try 5 minutes out (like the notification emails), so two workers never take the same meeting; the claim returns untracked snapshots and the service **loads the meeting again before it writes the result**. The result is applied for the version that was sent: if a member changed the meeting meanwhile, the event is kept but the meeting goes round again (`RecordSynced` / `RecordSyncFailure`). `Version` is also an EF concurrency token (`DbUpdateConcurrencyException` becomes a 409 in `ApplicationDbContext`), so two saves at once cannot undo each other. **The Google event id is the meeting's id** (`Meeting.EventId`, 32 hex digits, which Google accepts), so a try whose answer was lost cannot create a second event: the insert answers 409 and the client updates it instead. A new event is made with a Meet link (`conferenceData.createRequest`), the client as guest and `sendUpdates=all`, so **Google emails the client the invitation and every change or cancellation**; reminders are the calendar's own (`useDefault`). An event the organiser deleted in Google (404 / 410) is never brought back and counts as done; a meeting cancelled before it ever reached Google needs no call. Failures: `GoogleCalendarException` (down, busy, 5xx, network, 403 for rate limits) backs off 1, 5, 15 and 60 minutes, then `Failed` on the 5th try (or at once when the meeting is over); `GoogleAccessRevokedException` (token refresh `invalid_grant`, 401, 403 `insufficientPermissions`) or a missing / unreadable connection makes the meeting `NeedsReconnect` with no retry and the connection `NeedsReconnect`. `POST …/meetings/{id}/retry-sync` queues a `Failed` meeting again (409 otherwise, or when it is over). **Disconnecting Google** parks the organiser's open `Pending` / `Failed` meetings as `NeedsReconnect` and leaves the `Synced` ones (their events stay in Google); **connecting again** puts the `NeedsReconnect` ones that have not ended back in the queue. The responses carry `syncStatus` and `meetUrl` (the portal only `meetUrl`, and not for a cancelled meeting). Tests: the integration tests use `ApiFactory.Calendar` (`FakeGoogleCalendarClient`, failures and delays set per refresh token) and `SyncAll()`; `GoogleCalendarClientTests` checks the real client's requests against a fake HTTP handler.
- Members cannot be added through the API yet (invitations step); integration tests add them straight to the database.

## Adding a new feature (e.g. `Projects`)

Use `Clients` as the template. Every step is needed; nothing fails at build time if the DI lines are forgotten, the app only breaks on the first request.

1. **Domain**: `Domain/Entities/Project.cs` (private setters, static factory, throws `DomainException`); enums in `Domain/Enums/`.
2. **Application**: `Interfaces/Services/IProjectService.cs`, `Services/ProjectService.cs` (`internal`, calls `WorkspaceAccess` first if the data belongs to a workspace), `Interfaces/Repositories/IProjectRepository.cs`, `Mappings/ProjectMappings.cs`, `DTOs/Projects/` (requests and responses). One repository per aggregate, not per entity.
3. **Application DI**: register `IProjectService` in `Application/DependencyInjection.cs`.
4. **Infrastructure**: `DbSet<Project>` in `ApplicationDbContext`, `Persistence/Configurations/ProjectConfiguration.cs`, `Persistence/Repositories/ProjectRepository.cs`, and register `IProjectRepository` in `Infrastructure/DependencyInjection.cs`.
5. **Migration**: `dotnet ef migrations add <Name> ...` (see Database and migrations), then review the generated file.
6. **Api**: `Controllers/ProjectsController.cs`, thin, no error handling.
7. **Tests**: service tests in `tests/Partnr.UnitTests/Application/` (fake repository + fake unit of work), entity tests in `Domain/`.
8. Run `dotnet build` (0 warnings) and `dotnet test`.

External services (email, OAuth, AI, file storage) follow the same rule as repositories: the interface lives in `Application/Interfaces/Services/`, the implementation next to its kind of service in Infrastructure (`Email/`, `Storage/`, ...), never in `Persistence/`.

## Database and migrations

- PostgreSQL 17 via `docker-compose.yml` (db `partnr`, local-dev-only credentials `postgres`/`postgres`, port 5432). The `Postgres` connection string is in `src/Partnr.Api/appsettings.Development.json`. To use a different Postgres (e.g. one installed locally), override it with user secrets instead of editing that file: `dotnet user-secrets set "ConnectionStrings:Postgres" "Host=...;Password=..." --project src/Partnr.Api`.
- **Email** goes through `IEmailSender` (Application), implemented by `Infrastructure/Email/SmtpEmailSender` (MailKit) and configured by the `Email` section (`From`, `SmtpHost`, `SmtpPort`, `SmtpUsername`, `SmtpPassword`, `UseTls`), validated at startup. In development the SMTP server is **Mailpit** from `docker-compose.yml` (SMTP on 1025, inbox UI on http://localhost:8025): every email is caught there, none reaches a real inbox. Production only changes the configuration. Integration tests replace the sender with `FakeEmailSender` (`ApiFactory.Emails`); `Email/SmtpEmailSenderTests` checks the real sender against a Mailpit container.
- **File storage** goes through `IFileStorage` (Application), implemented by `Infrastructure/Storage/S3FileStorage` (AWSSDK.S3) and configured by the `Storage` section (`ServiceUrl`, `Region`, `Bucket`, `AccessKey`, `SecretKey`, `ForcePathStyle`, `CreateBucketIfMissing`), validated at startup. Any S3-compatible service works (AWS S3, R2, B2): production only changes the configuration and makes the bucket ahead of time. In development it is **RustFS** from `docker-compose.yml` (S3 API on http://localhost:9000, console on http://localhost:9001, dev credentials `rustfsadmin`/`rustfsadmin`, bucket `partnr` created on first use); MinIO no longer publishes images. `DeleteAsync` never throws (it logs), `OpenReadAsync` throws `NotFoundException` for a missing key. Integration tests replace the storage with `InMemoryFileStorage` (`ApiFactory.Files`); `Storage/S3FileStorageTests` checks the real adapter against a RustFS container.
- Migrations are created in Infrastructure, started from Api (commands work in any shell):

```bash
dotnet ef migrations add <Name> --project src/Partnr.Infrastructure --startup-project src/Partnr.Api --output-dir Persistence/Migrations
dotnet ef database update --project src/Partnr.Infrastructure --startup-project src/Partnr.Api
```

- **Client name is optional** (`Client.Name`, `ClientResponse.Name` are nullable): a card can be just an email. UIs show `name ?? email` until the client has an account, whose name replaces it.
- **Account suggestions** (`GET /api/workspaces/{id}/clients/suggestions?email=`, `ClientSuggestionService`) are a directory of accounts, so they are narrow on purpose: members of the workspace only (404 otherwise), at least 3 characters (an empty list below that), at most 5 results, a match on the start of the email only (never the name), workspace members left out. The endpoint has its own **rate limit** (`RateLimitPolicies.Suggestions`, 60 a minute per signed-in user, answering 429), defined in `Program.cs` with `AddRateLimiter`/`UseRateLimiter` (placed after authentication so it can follow the user). New endpoints that look people up should reuse that policy or add one next to it.
- **Test data (development only):** `-- --seed` (VS Code task `db-seed`) applies pending migrations and adds demo accounts, workspaces and clients, then exits. It is never automatic, so the e2e and integration databases stay empty. It is safe to run again: when `demo@example.com` exists it does nothing. **F5 ("API" launch profile) reseeds on its own when the seed changed**: it sets `Seed__ReseedOnChange=true`, and at startup the API compares a fingerprint of the seed's source (`SeedFingerprint`: `DevelopmentSeed.cs` and `DevelopmentDataSeeder.cs`, embedded in the assembly at build) with the one stored as the database's own comment (`COMMENT ON DATABASE`, no table). If they differ, or the database has demo data but no fingerprint, **every table is dropped (`DROP SCHEMA public CASCADE`), recreated by the migrations and seeded again, so anything entered by hand is lost**; it refuses a database that is not on localhost. It is off by default because the integration and e2e runs are in Development too; `dotnet run` without that variable never recreates anything (use `-- --seed` by hand).
